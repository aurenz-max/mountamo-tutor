# Lesson planner pilot

Production comparison: `node scripts/lesson-planner-production-ab.mjs --run --out qa/lesson-planner/production-ab/<new-run>` runs five curriculum objectives twice per arm, calling the real `generateExhibitManifestStreaming` (including its eval-mode resolver) for production. The experimental arm retrieves semantic candidates, plans once, and compiles its choices through the shared manifest enrichment function. Both arms then call the real component generators, package/assembly helpers, coverage judge and code scorer. Full frozen fixtures, source hashes, API prompts/model telemetry, generator data and masked replay packages are saved. `node scripts/lesson-planner-common-objective-eval.mjs <run-dir>` adds a separate evaluation-only normalization of objective identity/text, so production's synthetic IDs cannot turn one source objective into two scoring targets. Raw packages/verdicts remain unchanged. `node scripts/lesson-planner-production-report.mjs <run-dir>` builds comparative tables.

This is a fixed-objective planner comparison, not an independent test of topic-to-objective authoring. Each shared brief is generated once with the real curator and then has its objectives replaced with the exact supplied curriculum objective. Production receives its default settings; experimental retains its 15-minute request, while production exposes no duration parameter. Generator transport timeouts are 120 seconds in both arms. Two lessons run concurrently; reported full-generation latency ends when all their blocks finish, including caregiver blocks, and excludes the offline coverage judge. Scores are provisional instrument readings; masked Lesson Bench packages still require human playback/rating. The experiment never changes production source or appends to production evaluation logs.

Curriculum-objective sweep: `node scripts/lesson-planner-curriculum-ab.mjs --run` compares lexical and semantic discovery on 13 user-supplied ordinal/teen-number objectives. Kindergarten was explicitly retained to expose catalog limits. See [curriculum results](curriculum-ab/RESULTS.md). `--pipeline objective` uses the exact objective text as the discovery query and composes once with mode cards; it does not run open-topic arc generation. Evidence criteria are tester-authored and identical across arms. It preserves source objective IDs/text, full candidate provenance, retrieved pools, plans and gaps. Expected candidate IDs are report-only labels, including relevant tools whose grade limits may make them unsuitable for final selection. This is not an external curriculum-service lookup or hydrated lesson test.

Semantic discovery experiment: `node scripts/lesson-planner-discovery-ab.mjs --run` runs paired lexical/semantic open-topic plans for six original topics and three new probes. It resumes by skipping arms with saved JSON artifacts, including failed/invalid runs; use a new output directory for a fresh replicate. See [discovery results](discovery-ab/RESULTS.md). Expected candidate IDs are evaluation labels only; they are never included in planner fixtures or retrieval logic.

For one semantic run: `node scripts/lesson-planner-pilot.mjs --pipeline topic --catalog all --discovery semantic --fixture qa/lesson-planner/fixtures/open-topics/sea-otters.json`. The default remains lexical. Semantic discovery uses `gemini-embedding-001` with 768 dimensions, RETRIEVAL_DOCUMENT for catalog records and RETRIEVAL_QUERY for the raw topic, following [Google's embedding API](https://ai.google.dev/api/embeddings). Cosine ranking runs locally against a content-addressed cache in `qa/lesson-planner/discovery-cache`. Changing discovery text, model or dimensions rebuilds the index. Each new run embeds its topic; there is no query cache or additional generation stage.

Discovery cards are source-derived catalog projections: ID, teaching description, lesson roles, and separate evaluation-mode declarations. Only ID, description and roles are embedded. These are not yet curated entity/category tags or verified interaction contracts. Both arms retain the existing top-ten-plus-role-matches selection rule and general core/assessment pool; detailed downstream prompts and mode metadata stay unchanged. Record `latencyMs` measures planning, `onlineLatencyMs` adds query embedding and ranking, and `semantic.indexLatencyMs` separately reports offline index construction/cache loading. Runtime setup and file I/O are not included in online latency. No content is hydrated in this experiment.

Open-topic follow-up on the remaining five user topics: [results and caveats](open-topic-sweep/REPORT.md). `node scripts/lesson-planner-open-topics.mjs --run` creates topic-only fixtures and runs one plan each; it retains failures and all exact inputs. This sweep is distinct from the earlier fixed-objective twelve-run comparison.

Open-topic entry point: `node scripts/lesson-planner-pilot.mjs --pipeline topic --fixture qa/lesson-planner/fixtures/open-excavators.json --catalog all --out qa/lesson-planner/open-topic`. This rejects supplied objectives; existing objective-first arms remain unchanged. Discovery combines literal topic matches with per-role topical matches and the core/assessment pool. Two calls choose a learning arc, then bind/compose experiences with objective references. All discovery candidates, selected/deferred questions, evidence criteria and plans are saved. See [open-topic findings](open-topic/REPORT.md). This is still a heuristic neighborhood and catalog-declared metadata, not verified semantic retrieval. No preferred primitive IDs are encoded in the fixture.

Cross-topic pilot: [six-topic findings](topic-sweep/REVIEW.md). Reproduce fixture generation with `node scripts/lesson-planner-topics.mjs`; add `--run` for twelve live runs (one per arm/topic, full catalog, no retry). `node scripts/lesson-planner-topic-report.mjs` rebuilds the results index and summary from all saved runs in topic-sweep. Repeating the sweep accumulates artifacts rather than overwriting them; the report lists all runs.

A standalone, planning-only experiment from the objective-to-lesson design discussion. Uses the existing Gemini client and live catalog through Vite SSR. No dev server, production changes, hydration, coverage judging, or automatic repairs.

From `my-tutoring-app`:

```powershell
node scripts/lesson-planner-pilot.mjs --dry-run
node scripts/lesson-planner-pilot.mjs
node scripts/lesson-planner-pilot.mjs --representation mode-cards
node scripts/lesson-planner-pilot.mjs --pipeline staged
node scripts/lesson-planner-pilot.mjs --pipeline staged --catalog all
node --test scripts/lib/lesson-planner-pilot.test.mjs
```

Optional `--fixture <json>`, `--model <model>`, `--out <directory within app>`. Live calls require `GEMINI_API_KEY` in the environment or `.env.local`. Default model: gemini-flash-latest, low thinking, temperature 0.3; one call, 60-second timeout, no retry. Each invocation saves a unique JSON artifact; live calls also produce a readable Markdown review. Input snapshots include objective, learner, budget, candidate descriptions/modes/affordances, source-inspected notes, exact prompt/schema, hashes, model settings/version, usage, and latency. Credentials are never intentionally saved.

`--representation descriptions|mode-cards` switches only input presentation. Default remains descriptions. Mode cards flatten all primitive/mode pairs into primary selectable tasks, with shared primitive descriptions, constraints and notes in a supporting section. Primitives with no eval modes remain selectable with an empty mode. Raw mode affordance overrides are preserved alongside shared base facts. No additional capabilities, judgments or candidate filtering are introduced. Full canonical input and the presented view are both saved. See [mode-card comparison](mode-card-ab/REPORT.md) for the first three-per-arm experiment; it did not establish a quality win. This is a presentation experiment, not yet the richer verified instructional/evidence card system discussed.

`--pipeline staged` runs three bounded calls using the same model/settings: interpret the objective without catalog context; propose one task per instructional job from retrieved matches; compose those proposals with primitive/mode bindings preserved. Each call has a 60-second ceiling and no automatic retry/repair. It uses mode-card composition internally regardless of `--representation` (that option controls only the single arm). All intermediate prompts, schemas, responses, latency, usage, retrieval rankings and validation are persisted in `stages`. Top-level latency measures the entire planning pipeline. Top-level prompt is the initial call; inspect stages for subsequent prompts. Dry-run prepares inputs only and does not simulate dependent calls.

Retrieval is an intentionally transparent lexical, mode-weighted prototype with four tasks per instructional job. It searches either the fixture universe or `--catalog all` (entire live catalog) without an API call. Task count sent onward is bounded by four times the number of jobs, but verbose descriptions still affect token size. It is NOT verified semantic retrieval, and misses are not supply gaps. Stage validation checks objective identity, job completeness, dependency cycles, retrieval/proposal references, and final proposal bindings; it does not prove semantic fit or rendered dependency order. This pilot handles the fixture's single objective; multi-objective parallel proposals and cross-objective composition are not implemented yet.

See [staging experiment](staged-ab/REPORT.md). The full-catalog trial exposed a retrieval failure: generic explanation/opening/assessment candidates disappeared behind topical lexical matches. Do not promote this arm to production or read the resulting omissions as real catalog limitations. A staged run tests decomposition PLUS retrieval, not decomposition alone; a fair next ablation must hold retrieved candidates fixed.

The current candidate set includes ALL live core and assessment entries plus five explicitly selected measurement/engineering specialists (26 candidates in the September 6 run). Knowledge-check and fast-fact enter automatically through catalog membership. Included/excluded IDs and group provenance are saved. This tests bounded planning, NOT automated specialist retrieval or full-catalog recall. Most capability cards are catalog declarations, not verified implementations. Source-inspected notes are explicitly marked and may need review when their source changes. Grade K and 15 minutes remain unchanged pilot assumptions.

Structural validation checks objective identity, candidate/mode validity, unique experience IDs, audience, minutes, and whether each requirement is declared in the student plan or explicitly unmet. Each instructional contribution has one decision (provided/merged/partial/omitted), a reason and linked experiences. This is the authoritative place for instructional gaps; evidence gaps belong in `unmetRequirements`. These checks do not establish pedagogical quality or actual evidence coverage. `evidenceTargets` are intended opportunities only. An honest plan with supply gaps can be structurally valid.

See [realistic pilot review](realistic-pilot-review.md) for the broader-catalog runs, confirmed planner limitations, and the distinction between structural validity and lesson quality. No primitive count is forced, and estimated budget overruns remain visible warnings.

First review: does this feel complete, does every experience contribute something distinct, and does it accurately expose capability gaps? Keep/fix/cut the experiences before revising the contract. Do not tune the planner solely to this fixture.

After affirming the contract, add the baseline arm using the current manifest generator with fixed objective IDs/text, learner context and grade. Record model/settings and both baseline manifest plus resolver latency; the proposed arm uses one call and a curated shortlist, so an end-to-end A/B tests a bundle of changes. Isolate shortlist and planning-contract effects in later ablations. Include repeated baseline runs to measure sampling variance. Then compile the new plan into the executable manifest and hydrate both arms through the same existing generators; use Lesson Bench, lesson-coverage, and human ratings. A planning-only success is not a lesson-quality win.
