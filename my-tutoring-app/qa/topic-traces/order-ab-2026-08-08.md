# Ordering A/B — arm B (position-aware eval-mode resolution) — 2026-08-08

> ⚠️ **This whole study asked the wrong question.** It compares two variants of our own
> resolver prompt, which measures whether a candidate change moves anything — never
> whether what SHIPS is any good. Both arms shared the same wrong **objective** order,
> so neither could see the actual defect. The real answer is in
> `order-audit-2026-08-08.md`. Kept for the rejected-arm record and the pairing method.

**Verdict: arm B REJECTED. And the defect it was built to fix does not exist.**

Two runs. The first was invalid by construction; the second is the result.
Instrument: `npm run audit:order-ab -- <port> <pairs>`.

---

## What was tested

Arm A = HEAD. Arm B reconciles the conflict named in the handoff §4: the manifest
schema says component order carries a teaching arc, and `resolveLessonEvalModes`
rule 1 then forbids that stage from reading it (*"Never pick by lesson position,
phase, or 'introducing the tool'"*). Arm B shows each slot its `position: N of M`,
marks siblings `[earlier]`/`[later]`, and demotes the simplest-mode bias to a
tiebreak that an earlier sibling can consume.

12 topics — math, phonics, science, plus the excavator and dump-truck lessons as
controls. Blind pairwise judge (`gemini-flash-latest`, temp 0), presentation order
flipped on alternating pairs, arm honoured verified from the echoed response.

---

## Run 1 — INVALID, and worth recording as a method lesson

Arms ran as two independent traces with the same fixed objectives. Result 20-16
for B, p = 0.62.

That number means nothing. **35 of 36 pairs had a different component sequence in
the two arms** — the manifest is a separate LLM call, so each arm re-sampled its
own blueprint and the judge was comparing two different lessons. Freezing the
objectives was not enough; the dominant noise source was one stage further down.

Fixed by `experiment.compareArms`: generate ONE manifest with resolution skipped
(`evalModeArm: 'none'`), then resolve a structured clone of it under each arm. The
arms now differ by the resolver prompt and nothing else.

### Reading it

1. **Arm B is a no-op on more than half of all lessons** — 26/48 pairs identical,
   and 11 of 12 phonics pairs. Where the objective already pins the skill, telling
   the resolver about position changes nothing.
2. **Where it does act, it loses 9-13** and is flagged for reaching past the
   objective **6 times against arm A's 1**. Rule 3 ("later slots ask more") is an
   escalator, and escalation is wrong about as often as it is right:
   > *"Lesson 2 requires rapid subitizing, which introduces unnecessary visual
   > speed pressure for a first-time learner"* (place value)
   > *"Lesson 2's second activity asks students to classify shapes by geometric
   > property, overreaching the identification objective"* (shapes)

   It does buy a better first activity (19 vs 15 reachable) — arm A's simplest-mode
   bias was guarding against exactly the overreach arm B lets through. That guard
   is load-bearing.
3. **The within-block collapse does not exist.** 0 of 86 blocks resolved every
   slot to the same skill, under BOTH arms; 0 duplicate-skill pairs. The handoff's
   `6x explain → ten-frame/build, 6x apply → ten-frame/build …` table was
   aggregating **across lessons**, not within a block — it says "whenever ten-frame
   appears anywhere, it tends to get `build`", which is primitive-level dominance
   and may simply be correct. Cross-lesson spread, run 1 data:
   `sorting-station` sort_one ×11 / sort_variety ×1; `counting-board` count ×6/6;
   `ten-frame` build ×7 / subitize ×2.
   Whether that dominance is a defect is a **content** question about those
   primitives, not an ordering one — and it is not answered by anything in this lane.
4. **Controls held** (2-2), as expected: engineering lessons are 5/24 multi-mode,
   so there is almost nothing for this stage to decide there.

## What this closes

- **Arm B: rejected.** Kept in the tree, gated off, labelled — it is the
  counterfactual `compareArms` needs. Do not promote it.
- **B′ (deterministic `scaffoldingMode` sort): already killed by inspection** —
  same axis as the β sort the handoff itself rejected (886 within-primitive mode
  pairs, zero rank disagreements). Nothing here revives it; with 0/86 collapsed
  blocks there is not even a symptom left for it to treat.
- **Layer B, as a lane, is closed unless new evidence arrives.** Two proposed
  levers died — one to inspection, one to measurement. What actually moved lesson
  quality this session was Layer A (objective Bloom order, 83% → 100%) and the
  hundreds-chart window fix. The user's read going in — *"the Bloom model works
  great and intelligently packs the order, we don't need significant new
  infrastructure"* — is now measured rather than intuited.

## What is left, if anything

The only live question the data raises is #3 above: is `sorting-station → sort_one`
in 11 of 12 appearances (or `counting-board → count` in 6 of 6) the right call?
That is a per-primitive content question for `/topic-fidelity` or
`/primitive-contract`, one primitive at a time — **not** a manifest-stage or
ordering change. File it there or drop it; do not reopen ordering to chase it.

## Method notes for the next run

- **Pair on the manifest, not the objectives.** Run 1 is the cautionary tale.
- **Count the identical pairs.** They cost no judge call and they are the finding:
  "arm changes nothing 54% of the time" is more informative than its win rate.
- **`fileURLToPath`, never `url.pathname`** — the repo path contains a space, which
  `pathname` leaves percent-encoded; all three harnesses had this and silently
  wrote nowhere. Fixed in all three.
- **A no-op arm inflates ties.** Report win/loss over the pairs that differed, not
  over all pairs, or a do-nothing arm scores 50%.
