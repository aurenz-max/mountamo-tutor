# Ten-frame on the teaching workspace — W1 pilot (2026-09-22)

Handoff 15, step 2 (first half). Executor `/add-live-tutor-tools`.

## What shipped

All seven catalog modes (`build`, `make_ten`, `subitize`, `decompose`, `build_teen`, `decompose_teen`,
`operate`) bind the shared workspace in the live host and in ordinary lessons (`bindsTeachingWorkspace`).
Outside a live runtime, and for a runtime mount with no resolved pin, the scripted runner path is unchanged.

**The shape of a W1 binding (pilot question 1).** No `*Teaching` component and no domain extraction.
`TenFrame.tsx` swaps its controller at the component boundary, keyed so hooks never change owner:
`useTenFrameTutorController` (workspace, 110 lines incl. the interface) or the runner. Counting Board's
`CountingController` is the precedent. The surface keeps its rendering, frame rules and code judges;
the new pure module `tenFrameWorkspace.ts` (70 lines) holds the assignment, scene facts and the response
description. The runner is never mounted on the workspace path (its context push would run beside the tutor).

**One progression owner (question 2).** The frame never advanced itself; the runner did. On the workspace
path the runner is absent, the observer or the shell's Try again / Next challenge progresses, and the
frame's own stillness commit (R6) stays as the learner's submit, not a progression clock.

**Adapter (question 3).** `tenFrameLive.ts` is now the shared workspace shape (`workspaceLessonStart`,
`workspaceGuidance` with three domain sentences). Not yet generated from the catalog: every field is still
hand-written. That generic adapter is the next pilot step, on number-bond.

**Journey row.** `execution: 'workspace'`, inputs derived from `tenFrameHarnessAnswers` and the frame's
real cells. W1 offers no `demonstrate`; `present` is offered only on `subitize`.

## Defects the drives found, fixed in this slice

1. **Retry un-saw the flash (component).** A workspace retry reset `subitize` to "not presented", so the
   learner's second answer was never opened as a response and the tutor's "That's right" credited nothing
   (stall). A retry of a presented quick look now stays answerable; re-showing records assistance.
2. **The first look waited on a tool call (component).** On item 2 of one run the tutor never called
   `present`; the item could not become answerable. The learner now has a **Show me** button for the first
   look (unassisted), beside the existing Show again.
3. **Shared harness: a gesture checked wrong could only reopen by the observer.** When the tutor coached
   ("How many more do you need to add?") without inviting a retry, the frame stayed locked and the journey
   timed out. In the product the learner presses the shell's Try again. The journey now does the same,
   recorded as `learner_pressed`, after asking aloud first. Driver gains `learner_progress`.
4. **Shared harness: a `<no speech>` provider turn counted as the tutor's reply**, so the journey answered
   twice before the tutor spoke ("3 2"). Markup-only turns (also cut-off `<no `) are skipped, matching
   `DialogueObserver`. Note: the frontend's `hasSpokenWords` misses the cut-off `<no ` form; not changed here
   (shared observer change, needs its measurement).
5. Driver `touch` accepts a named object (`target: 'cell-3'`); `JourneyContext` carries the runtime `demand`.

## Mixed and blended pins (Auto mode)

A `mixed` or `a|b` pin binds when every mode it names binds (`pinBindsWorkspace`), which for ten-frame is
always. Everything that differs by kind is read per item, not per session: response channel (placement or
speech), whether `present` is offered, readiness, the published spoken key, the seeded frame, and the split
ledger across items. Recording: `metrics.evalMode` is the first item's mode and the learning responses carry
the pin, exactly as on the scripted path; per-item recording is the queued `/student-data-loop` item.

- Component test: `mixed` and `build|subitize|decompose`, build → subitize → split to completion, 2/2.
- Real `mixed` generation at K: 7 challenges over build, subitize, make_ten, split (single frame; teen items
  are dropped at K by the generator, R2). The journey mounts two challenges per run, so two drives:
  build → subitize PASS (`ten-frame-w1-mixed-audio-2026-09-22.json`; the learner pressed **Show me**),
  make_ten → split PASS on the same payload reordered (`-b.json`, `…mixed-payload-2026-09-22-reordered.json`).
  In `-b` the tutor coached twice without a verdict and the learner pressed **Try again**, the first drive
  where that fallback was needed.
- Not driven connected: `operate` (Grades 1-2) and the teen modes inside a mixed session.
